# BAR → Web: Phase 2 (Recoil 2026.07.04)

Continues [BAR-web-phase1-scoping.md](BAR-web-phase1-scoping.md). Phase 1 ended with M4: the headless engine, built with Emscripten, plays a native BAR replay to the end under Node with 450/450 sync checksums. Phase 2 moves to the browser: first headless, then the renderer and audio.

## Milestones
- **B1**: the same headless replay plays to the end in a Chromium tab with no desync, and the tab stays responsive. No renderer or audio. **Done 2026-11-14.**
- **B3** (audio), **B4** (live play), **B5** (static delivery build): built 2026-11-17 and only partly run (the user took over playtesting); see the last section. **B6**: design only.
- **B2**: the renderer in the browser: the engine draws the game (world, units, UI) into a canvas through WebGL2. **In progress**: sky, textured terrain, map features and BAR's LuaUI render with the cross-compiler now enabled by default. Basic WebGL2 LuaVAOs let scum initialize, and enabled/default renderer replays pass 450/450. Units, build stages (clip planes), engine UBOs and the sharpening pass now render. The reflection cubemap renders since its depth renderbuffer gets a sized format. The depth-buffer copy (ground decals, soft particles) now blits. The recurring GL errors are attributed to their calls (`?glcheck=1`). The shadow-sampler, `CMetalExtractionTexture` and DDS-mipmap errors are fixed, and a full `?trace=1` replay logs no GL error at any draw. Wire build stages (`glPolygonMode`) and depth `CopyToTexture` are emulated. What remains: SSBO GL4 widgets, CUS GL4, geometry-shader variants, and a LuaVAO instanced-draw error seen only in slow `glcheck` runs. See the 2026-11-16 continuations below.

**Design**
- New target **`engine-web`** (`rts/builds/web/`): the engine sources without `HEADLESS`, with `RECOIL_WEB_RENDER` defined, linked against Emscripten's SDL2 port and WebGL2 (`-sMIN/MAX_WEBGL_VERSION=2 -sFULL_ES3 -sOFFSCREENCANVAS_SUPPORT -sOFFSCREENCANVASES_TO_PTHREAD=#canvas`) on top of `RECOIL_WASM_WEB_LINK_OPTIONS`. `NO_SOUND`. Output `spring-web.{js,wasm}`.
- **Main loop:** `SpringApp::Run()` is split into `RunIteration()` and `RunEnd()`; all builds use them. With `RECOIL_WEB_RENDER`, `Run()` registers `emscripten_set_main_loop_arg` (one iteration per requestAnimationFrame, because a frame drawn to an OffscreenCanvas only reaches the page when the worker returns to its event loop) and returns. A 50 ms worker timer also runs an iteration when no animation frame came for 100 ms, because a hidden tab gets none. `Main.cpp` leaks the `SpringApp` so it outlives `main()`. `RunEnd()` runs from the last iteration, then `emscripten_force_exit`.
- **Context:** SDL's Emscripten backend creates GL contexts through EGL on the page's main thread, which can't use a canvas transferred to the engine's worker. `GlobalRendering.cpp` maps `SDL_GL_{Create,Delete}Context/MakeCurrent/SwapWindow` to `WebGLCompat` (html5 WebGL API, called from the worker); VSync is a no-op.
- **`Rendering/GL/WebGL/`, the desktop-GL shim** (all new). The engine wants a desktop GL 3.0+ compatibility context through glad. The shim loads glad from Emscripten's WebGL2, reports a desktop version (`3.0 WebGL2-compat (...)`) and 97 extensions, fills the ~2,660 entry points WebGL2 lacks with counting no-op stubs (generated by `gen_stubs.py` from `glad.h`; the stubs used are logged every 20 s), and replaces selected entry points:
  - `WebGLState.cpp`: matrix stacks, fog, lights and current colour on the CPU, uploaded as `rcl_*` uniforms to programs whose shaders use the `gl_*` built-ins; client-state arrays mapped to generic attributes; desktop-only enable caps; `GL_QUADS` (as indexed triangles), `GL_QUAD_STRIP`, `GL_POLYGON`; `glPushAttrib`/`glPopAttrib`; a per-VAO shadow of the vertex-attribute state (new, see below).
  - `WebGLShaderTranslate.cpp`: text translation of desktop GLSL (≤ 1.50 style) to ESSL 3.00: `gl_*` built-ins become `rcl_*` uniforms and attributes, `texture2D` and friends, `varying`/`attribute`, fragment outputs with explicit locations, uniform initializers stripped (set after link), interface blocks flattened, extension `#if`s neutralized.
  - `WebGLObjects.cpp`: `glMapBuffer*` emulation, texture bookkeeping (for `glGetTexLevelParameter`), desktop → GLES internal-format mapping, BGR(A) swizzling on upload.
  - `WebGLImmediate.cpp`: `glBegin/glEnd`, `glRect`, a fixed-function emulation program for draws with no shader bound (vertex colour, one texture, alpha test), display lists as recorded closures.
  - `WebGLCompat.cpp`: loader, version/extension spoofing, stub statistics, the `RECOIL_WEB_CAPTURE` frame dump and `RECOIL_WEB_TRACE` draw trace (debug aids), and `Canary()` (a static-data corruption checker, currently not called anywhere).

The log shows `[DemoSync] summary: 450 demo checksums matched, 0 mismatched` with no `[DESYNC WARNING]`. Harness: `C:\Beyond All Reason Web\web-harness\` (page, OPFS loader, COOP/COEP server, content packer; see its README). The full browser log is in `web-harness/logs/infolog-browser.txt`.

**Design**
- New target **`engine-headless-web`** (`spring-headless-web.{js,wasm}`). It links the same objects as the Node `engine-headless`: on WASM the engine sources are now an OBJECT library, so they compile once. Its link options are in **`RECOIL_WASM_WEB_LINK_OPTIONS`** (top-level `CMakeLists.txt`): `-sENVIRONMENT=web,worker -sWASMFS=1 -sPROXY_TO_PTHREAD=1` plus the same memory, stack, pthread-pool and exception settings as Node, `-sEXPORTED_RUNTIME_METHODS=wasmMemory`, and `--pre-js rts/lib/wasm-stubs/web-pre.js`. `RECOIL_WASM_BUILD_WEB` (default ON) turns the target off. The Node target and the unit tests keep `RECOIL_WASM_NODE_LINK_OPTIONS`, unchanged.
- **Main loop off the main thread:** with `PROXY_TO_PTHREAD`, `main()` (and `SpringApp::Run`'s busy loop) runs in a worker. The page's main thread only services proxied calls, stdout/stderr forwarding and worker spawning. The phase 1 `emscripten_main_thread_process_queued_calls()` call is now guarded with `emscripten_is_main_runtime_thread()` (it asserts otherwise).
- **File system:** WASMFS with the OPFS backend. `rts/System/Platform/Emscripten/WebFS.cpp`, linked into the web target only, mounts the OPFS root at `/recoil` (the fixed exe dir from phase 1). It's called through a weak hook at the very start of `main()`. Content is read outside the wasm heap. Layout: `/recoil/{base,maps,packages,pool,demos,write}`, run with `SPRING_DATADIR=/recoil/write:/recoil --write-dir /recoil/write`. The page passes the environment as `Module.recoilEnv`, which `web-pre.js` copies into `ENV`.
- **Content:** only what this replay needs, 2,054 MB. That's the game's rapid package `44fd01f1….sdp` plus its 18,358 distinct pool files (1,987 MB; it's the 19k-file `test-31943-6cd6caa`, not the 2,755-file Chobby package), the map `all_that_glitters_v2.2.sd7` (54 MB), base content (7 MB) and the replay. `pack-content.py` stages them with their mtimes and writes five bundles, each its files concatenated in manifest order. A dedicated worker (`opfs-loader.js`) streams them into OPFS through sync access handles.
- **Pre-built archive cache:** `build-cache.sh` plays the replay natively against the staged subset only. That writes `ArchiveCache22.lua`, and its 450/450 proves the subset is complete. The packer rewrites the cache's paths to `/recoil/...` and ships it in the write dir, so the browser never hashes the game.
- **OPFS caching between visits:** content bundles stay in OPFS and are fetched again only when their id (a hash of names, sizes, mtimes) changes. `write/` and the small `run` bundle are rebuilt on every load, and `?fresh=1` wipes everything. Keeping content cached between visits was confirmed as the intended policy on 2026-11-14.

**Caveats / open items**
- **Heap headroom:** 2.8 GiB of the 4 GiB wasm32 maximum for a 15-minute 1v1 AI game. Longer or bigger games (more units, raptors/scavengers) could hit the ceiling. Options: memory64 (`-sMEMORY64`, all of Chromium's 4 GB+ limits apply), `TextureMemPoolSize=0` for headless (it reserves 512 MiB at start), or trimming Lua mem use. Keep `VFSCacheArchiveFiles = 0` for the browser.
- **One-off main-thread stalls:** in one run, 222 ms during BAR's widget loading (a burst of several hundred log lines in about a second, each forwarded to the page and `console.log`ged); in another run, 265 ms at engine start while Emscripten spawns its 32 pool workers; 283–324 ms at exit, when `EXIT_RUNTIME` joins pthreads from the main thread (Emscripten warns "Blocking on the main thread is very dangerous"). The sim phase itself never stalls the page. Batching the log forwarding, and dropping `EXIT_RUNTIME` for the web target, would remove most of this.
- **Content files vanished from OPFS once (not reproduced).** In one cached reload (the run right after a passing one, between which the server was restarted), the loader found `.bundles.json` missing and wrote all 2,054 MB again. The engine then still saw no `mtimes.tsv`, base archives or demo, and failed with "Demofile not found" (exit −1003). Afterwards every *file* outside `write/` was gone, including the root's `mtimes.tsv`, while all directories (even the 256 pool dirs) remained and OPFS usage still read 2,062 MB. Two later runs with a 2 s file-count watcher (`?watchfs=1`), one fresh and one cached, kept every file through load, sim, exit and after. Nothing in the harness or engine removes files outside the write dir. BAR LuaUI's `os.remove` users (`cmd_map_project`, `gui_pip` stale segments) are prefix-bound or user-triggered, and the sandbox in `barwidgets.lua` limits them to user write paths. Suspects: Chromium OPFS state across the desktop app's pane, or WASMFS/OPFS interaction with entries left over from a previous page. **Mitigation:** the loader now spot-checks every cached bundle (first, last and 64 more files, existence and size) and re-fetches a damaged one. That's tested by deleting the map from OPFS: only the 54 MB map bundle was fetched again, then PASS.
- **OPFS space isn't reclaimed promptly:** after a `?fresh=1` wipe and later rewrites, `navigator.storage.estimate()` reported 4,115 MB in use for 2,054 MB of content. Deleted and overwritten files keep counting against quota for a while. Re-fetching bundles in place rather than wiping avoids most of it.

### 2026-11-16: B2 continued — depth-buffer copy blit fixed

Claude Code did this follow-up: investigation, shim change, builds, replays and capture inspection. No human verification or upstream contribution is claimed.

**Cause.** `DepthBufferCopy::MakeDepthBufferCopy` (called from `CWorldDrawer::DrawOpaqueObjects`) blits the default framebuffer's depth into a texture every frame. That texture is read by ground decals (`GroundDecalHandler`) and soft particles (`ProjectileDrawer`, unit 15). WebGL2 blits depth only between identical depth/stencil formats. **Fix, commit `e013691`.** `glBlitFramebuffer{,EXT}` are hooked. Before a depth blit between the default framebuffer and an FBO, the hook queries the attachments. If the default framebuffer is 24-bit depth with 8-bit stencil, and the FBO's depth attachment is a 2D texture with 24-bit depth and no stencil, that texture level is re-specified as `DEPTH24_STENCIL8`. The name and size stay the same, it stays attached, and it samples the same depth values. This happens once per texture (the formats match afterwards, so the check stops there). Immutable textures, renderbuffers and FBO-to-FBO blits are left alone. It is logged once per texture. The texture-level query records (`glGetTexLevelParameter`) keep reporting the format the engine asked for.

### 2026-11-17: WebGL profiling, state read-back cache (Firefox lag)

The user's Firefox log (`bar-web-log(1).txt`, Firefox 160) had no `[perf]` line in the 93 s after load, so fewer than 300 draw frames: **under about 3 fps**, against 21–26 fps in Chrome.

- `?glprofile=1` (render.js): the engine script loads as a blob with a wrapper in front that times every `WebGL2RenderingContext` method in the engine's workers (Emscripten starts its workers from the main script's URL). Every 5 s it posts `[glprof]` lines with call counts and time per method, with `getParameter`/`getError` split by argument. The report runs inside the wrapped `clear()`: the engine thread never yields, so timers don't fire there.
- Chrome, pregame, before: 32–36% of the engine thread inside WebGL, nearly all of it `getParameter` (~16,000/s: blend func/equation, color mask, cull face, front face, polygon offset, depth func/mask, line width, unpack row length), plus `getError` from the upload checks. The engine saves and restores state around draws by reading it back right after setting it.
- Commit `3898143438`: `web-pre.js` keeps a per-context copy of that state, written through by the setters (invalidate-only missed every read, because each read follows a set), plus ARRAY/ELEMENT_ARRAY buffer bindings. The texture upload paths read `glGetError` only with `RECOIL_WEB_TRACE`/`RECOIL_WEB_GLCHECK`.
- Chrome after: 7–11% of the engine thread in WebGL; no GL errors logged, no page errors, and the pregame picture looked the same as before. The values are recorded without checking for GL errors, so an invalid setter call would leave the copy wrong until the next valid set.
- **Not measured in Firefox yet.** Firefox may answer some of these queries on its own side already; a Firefox `?glprofile=1` log is needed to see what is left there.
- Firefox `?glprofile=1` run (`bar-web-log(2).txt`) after `3898143438`: in-game **27–34 fps** (was under 3). Still 74% of the engine thread in WebGL, 55% of it in `getParameter(ACTIVE_TEXTURE)` (0.22 ms a read in Firefox). The next commit caches that too.
